# 项目运行缺口归档 - 2026-05-02

## 当前结论

IoT Link RTU 当前已经具备部分联调能力，但距离“采集数据从串口设备进入系统，并在前端看到真实实时/历史/趋势数据”的完整闭环还差若干运行条件和实现环节。

当前可优先跑通的链路是：

```text
serial-collector -> rtu-gateway -> MQTT Broker
serial-collector -> rtu-gateway -> web-server 认证/在线状态
web-server -> PostgreSQL 管理数据查询
```

当前尚未完整闭环的链路是：

```text
rtu-gateway -> MQTT Broker -> web-server 订阅 -> 时序数据库落库 -> 前端趋势图
web-server 配置更新 -> MQTT 配置下发 -> rtu-gateway -> serial-collector 热更新/下发设备
```

## 必备运行条件

### 1. JDK 和 Maven

需要：

- JDK 17+
- Maven 3.8+

用途：

- 编译并运行 `serial-collector`
- 编译并运行 `rtu-gateway`
- 编译并运行 `web-server`

### 2. PostgreSQL

已用于管理数据存储。

需要确认：

- PostgreSQL 已启动
- 数据库 `iot_link_rtu` 已创建
- `iotiLinkRtu-web-server/src/main/resources/init-db.sql` 已执行
- 至少存在与采集器配置匹配的 RTU 记录

当前管理表：

- `rtu_gateway`
- `rtu_config`
- `rtu_alarm`

注意：

- PostgreSQL 不建议长期存储高频采集数据。
- 采集数据应迁移到时序数据库。

### 3. MQTT Broker

当前还未准备，是必须补齐的运行条件。

可选：

- Mosquitto
- EMQX

默认配置：

```text
tcp://localhost:1883
```

用途：

- `rtu-gateway` 发布 RTU 数据、状态、报警消息
- 后续 `web-server` 订阅消息并落库
- 后续配置下发通道

### 4. 虚拟串口对

如果没有真实串口传感器，需要准备一组虚拟串口对。

示例：

```text
COM3 <-> COM4
```

建议：

- `serial-collector` 打开 `COM3`
- 串口模拟器打开 `COM4`

当前默认串口参数：

```text
baudrate = 4800
data bits = 8
stop bits = 1
parity = None
```

### 5. 串口模拟器

需要支持十六进制收发，最好支持自动应答。

collector 默认会发送：

```text
01 03 00 00 00 02 C4 0B
```

模拟器应返回：

```text
01 03 04 02 92 FF 9B 5A 3D
```

```text

```


```text

```

MQTT：

```text
tcp://localhost:1883
```

web-server API：

```text

```

配置文件：

```text
iotLinkRTu-rtu-gateway/src/main/resources/config.properties
```

### serial-collector

当前默认：

```properties
rtu.id=ZM611116
rtu.secret=momingqinxlinknb
gateway.host=localhost
gateway.port=8888
serial.port=COM3
serial.baudrate=4800
modbus.device.address=0x01
collect.interval=1
```

配置文件：

```text
iotLinkRtu-serai-collector/src/main/resources/config.properties
```

数据库中必须有匹配记录：

```text
rtu_gateway.rtu_id = ZM611116
rtu_gateway.secret = momingqinxlinknb
rtu_gateway.status = ENABLED
```

## 主要缺口

### 1. MQTT Broker 尚未搭建

这是当前运行全链路的首要缺口。

未搭建时：

- `rtu-gateway` MQTT 客户端无法连接
- 数据无法发布到 MQTT
- 无法验证 MQTT 主题
- 后续 web-server 订阅落库无法进行

### 2. web-server 尚未实现 MQTT 订阅落库

当前 `rtu-gateway` 会发布数据到 MQTT，但 `web-server` 还没有订阅客户端。

缺少：

- 订阅 `iot/rtu/+/data`
- 解析数据消息
- 写入时序数据库
- 订阅 `iot/rtu/+/alarm`
- 写入报警表或触发报警处理
- 订阅状态主题并同步状态

### 3. 时序数据库尚未接入

项目设计中应使用时序数据库存储高频采集数据。

建议方案：

- 使用 TDEngine 存储 `rtu_data`
- PostgreSQL 只存管理数据

目标结构：

```text
PostgreSQL:
  rtu_gateway
  rtu_config
  rtu_alarm

TDEngine:
  rtu_data
```

需要补齐：

- TDEngine 服务
- TDEngine 初始化脚本
- TDEngine JDBC 依赖
- TDEngine 数据源管理器
- `RtuDataDao` 改为查 TDEngine
- MQTT 数据落入 TDEngine

### 4. 配置下发链路尚未完成

当前配置接口只更新数据库。

未完成链路：

```text
web-server 更新配置
-> MQTT 发布配置请求
-> rtu-gateway 订阅配置主题
-> 转为二进制/Modbus 命令
-> serial-collector 接收命令
-> 更新运行参数或下发串口设备
-> 返回配置结果
```

当前实际情况：

- `web-server` 没有发布配置 MQTT 消息
- `rtu-gateway` 的 MQTT `messageArrived` 仍是 TODO
- `serial-collector` 有接收网关命令并转发串口的处理入口
- `serial-collector` 的采集间隔当前来自本地配置 `collect.interval`

因此：

- 改数据库里的 `samplingInterval` 不会让运行中的 collector 自动变频。
- 实际改变采集频率仍需修改 collector 配置文件并重启。

### 5. 采集数据真实入库尚未闭环

当前真实串口采集数据可以到达：

```text
serial-collector -> rtu-gateway -> MQTT
```

但尚未自动进入：

```text
时序数据库 / 前端趋势图
```

需要补：

- web-server MQTT 订阅
- 数据消息解析
- 数据写入 TDEngine
- 查询接口读取 TDEngine

### 6. 文档部分内容需要同步更新

已有文档中部分内容已经过时。

需要更新：

- `doc/串口模拟联调测试说明.md`
- `README.md`
- 数据库设计文档中的 PostgreSQL/TDEngine 边界
- API 文档中配置下发的实际状态

重点修正：

- 实时/历史/统计接口不应再描述为 mock
- 配置下发应标注“当前仅保存数据库，尚未热下发”
- 采集数据存储方向应明确为 TDEngine

## 推荐启动顺序

```text
1. 启动 PostgreSQL
2. 执行 PostgreSQL 初始化脚本
3. 启动 MQTT Broker
4. 启动 web-server
5. 启动 rtu-gateway
6. 创建虚拟串口对
7. 打开串口模拟器并配置自动应答
8. 启动 serial-collector
9. 打开前端页面验证
```

## 推荐推进顺序

### 第一阶段：跑通基础联调

目标：

```text
collector -> gateway -> MQTT
gateway -> web-server 在线状态
```

需要完成：

- 搭 MQTT Broker
- 准备虚拟串口
- 准备串口模拟器
- 确认 PostgreSQL 中存在测试 RTU

### 第二阶段：补齐真实数据入库

目标：

```text
MQTT 数据 -> web-server -> TDEngine -> 前端趋势图
```

需要完成：

- 接入 TDEngine
- web-server 增加 MQTT 订阅
- 采集数据写入 TDEngine
- 数据接口改查 TDEngine

### 第三阶段：补齐配置下发

目标：

```text
前端/接口改配置 -> 运行中的 collector 生效
```

需要完成：

- web-server 发布配置 MQTT 消息
- gateway 订阅配置主题
- gateway 转发命令到 collector
- collector 更新运行参数
- 配置响应回传

## 当前最短可运行方案

如果只是先验证整体基本运行：

1. PostgreSQL 已就绪
2. MQTT Broker 搭好
3. 数据库插入 `ZM611116`
4. 虚拟串口 `COM3 <-> COM4`
5. 串口模拟器自动回复 Modbus 响应
6. 启动三个 Java 模块

可观察：

- collector 认证成功
- collector 采集成功
- gateway 解析温湿度
- MQTT 收到 `iot/rtu/ZM611116/data`
- PostgreSQL 中 `rtu_gateway.online = ONLINE`

暂不可期望：

- MQTT 数据自动入时序库
- 配置修改后热下发到 collector
- 真实采集数据自动出现在前端趋势图
