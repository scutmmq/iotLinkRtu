# 串口模拟联调测试说明

## 1. 当前已完成范围

- `serial-collector -> rtu-gateway -> web-server 认证接口` 已打通。
- `serial-collector -> rtu-gateway -> MQTT 发布` 已打通。
- `RTU 注册/列表/详情/更新/删除` 已接 PostgreSQL。
- `RTU 配置查询/更新` 已接 PostgreSQL。
- `报警列表/处理` 已接 PostgreSQL。
- `gateway` 会在认证成功、心跳、断开连接时同步 RTU 在线状态到 `web-server`。
- `serial-collector` 已改回真实读取串口返回值，串口模拟器发送的数据会生效。

## 2. 目前还没有完成的需求

以下功能仍未完成，测试时不要按“已可用”理解：

1. `web-server` 还没有 MQTT 订阅客户端。
2. `web-server` 还没有把 `gateway` 发布的 MQTT 数据真正入库。
3. `实时数据/历史数据/统计数据` 三个接口目前仍是模拟返回。
4. `gateway` 端虽然有 MQTT 客户端，但还没有实现“订阅配置主题 -> 转 Modbus 下发到 collector”的完整逻辑。
5. TDEngine 时序数据存储尚未接入。
6. 仓库里还有少量旧的 mock controller 文件未清理，但当前路由实际走的是已接数据库的那一套。

结论：

- 你现在可以测“串口采集 + RTU 认证 + 网关解析 + MQTT 发布 + 在线状态同步”。
- 你现在还不能测“前端/接口查真实采集历史”“MQTT 配置下发到串口设备”这两条完整链路。

## 3. 推荐测试目标

建议先做最小闭环测试：

1. 用虚拟串口对模拟一个 Modbus 温湿度传感器。
2. 启动 `web-server`。
3. 启动 `rtu-gateway`。
4. 启动 `serial-collector`。
5. 用串口模拟器在虚拟串口另一端返回合法 Modbus 响应帧。
6. 观察：
   - `collector` 日志是否显示“认证成功”“采集成功”
   - `gateway` 日志是否显示“RTU 认证成功”“温度/湿度解析成功”
   - MQTT Broker 是否收到 `iot/rtu/{rtuId}/data`
   - `rtu_gateway.online` 是否更新为 `ONLINE`

## 4. 测试前置条件

### 4.1 软件和服务

你至少需要准备：

- JDK 17
- PostgreSQL
- 一个 MQTT Broker，例如 Mosquitto 或 EMQX
- 一组虚拟串口对，例如：
  - com0com
  - Eltima Virtual Serial Port
  - FabulaTech Virtual Serial Port
- 一个串口调试/模拟工具，能够打开虚拟串口并按十六进制收发数据

### 4.2 当前默认配置

当前代码默认配置如下：

`web-server`

- HTTP 端口：`8081`
- PostgreSQL：`jdbc:postgresql://localhost:5432/iot_link_rtu`

`rtu-gateway`

- TCP 监听端口：`8888`
- MQTT Broker：`tcp://localhost:1883`
- 认证接口地址：`http://localhost:8081`

`serial-collector`

- `rtu.id=ZM611116`
- `rtu.secret=momingqinxlinknb`
- `gateway.host=localhost`
- `gateway.port=8888`
- `serial.port=COM3`
- `serial.baudrate=4800`
- `modbus.device.address=0x01`
- `collect.interval=1`

### 4.3 虚拟串口建议

如果你创建了一对虚拟串口，例如 `COM3 <-> COM4`：

- `serial-collector` 配置使用 `COM3`
- 串口模拟器打开 `COM4`

双方参数保持一致：

- 波特率：`4800`
- 数据位：`8`
- 停止位：`1`
- 校验位：`None`

## 5. 数据库准备

最简单的做法是直接插入一条与 `serial-collector` 当前配置一致的测试 RTU。

```sql
INSERT INTO rtu_gateway (
    rtu_id, name, location, serial_port, status, online, secret
) VALUES (
    'ZM611116', '串口模拟测试 RTU', '本机虚拟串口', 'COM3', 'ENABLED', 'OFFLINE', 'momingqinxlinknb'
)
ON CONFLICT (rtu_id) DO UPDATE SET
    name = EXCLUDED.name,
    location = EXCLUDED.location,
    serial_port = EXCLUDED.serial_port,
    status = 'ENABLED',
    online = 'OFFLINE',
    secret = EXCLUDED.secret;

INSERT INTO rtu_config (
    rtu_id, interval, modbus_device_address, baud_rate,
    temp_threshold_min, temp_threshold_max,
    humidity_threshold_min, humidity_threshold_max,
    alarm_enabled
) VALUES (
    'ZM611116', 1, 1, 4800, 18.0, 28.0, 40.0, 60.0, TRUE
)
ON CONFLICT (rtu_id) DO UPDATE SET
    interval = EXCLUDED.interval,
    modbus_device_address = EXCLUDED.modbus_device_address,
    baud_rate = EXCLUDED.baud_rate,
    temp_threshold_min = EXCLUDED.temp_threshold_min,
    temp_threshold_max = EXCLUDED.temp_threshold_max,
    humidity_threshold_min = EXCLUDED.humidity_threshold_min,
    humidity_threshold_max = EXCLUDED.humidity_threshold_max,
    alarm_enabled = EXCLUDED.alarm_enabled;
```

如果你不想手工插库，也可以调用注册接口，但那样 `secret` 会自动生成，你需要再把生成的 `secret` 回填到 `serial-collector` 配置文件。

推荐顺序：

1. 启动 PostgreSQL
2. 执行 `iotiLinkRtu-web-server/src/main/resources/init-db.sql` 或上面的测试 SQL
3. 启动 MQTT Broker
4. 启动 `web-server`
5. 启动 `rtu-gateway`
6. 建好虚拟串口对并打开串口模拟器
7. 启动 `serial-collector`

## 7. 串口侧应答机制

这里不是“设备主动上报”，而是 `serial-collector` 每秒主动发一条 Modbus 读取命令。

也就是说，串口模拟器需要做的是：

1. 收到采集器发来的请求帧
2. 返回合法响应帧

### 7.1 采集器会发送的请求帧

读取温湿度的请求帧固定是：

```text
01 03 00 00 00 02 C4 0B
```

含义：

- `01`：设备地址
- `03`：读保持寄存器
- `00 00`：起始寄存器地址
- `00 02`：读取 2 个寄存器
- `C4 0B`：CRC16

### 7.2 你应该回给采集器的合法响应帧

推荐先用这一帧：

```text
01 03 04 02 92 FF 9B 5A 3D
```

解析结果：

- 湿度：`0x0292 = 658 -> 65.8 %RH`
- 温度：`0xFF9B = -101 -> -10.1 C`

这是当前代码和文档都能正确解析的一条标准响应。

## 8. 如何在串口模拟器里发

你有两种方式：

### 8.1 手工应答

适合先看链路是否通。

步骤：

1. 打开串口模拟器，连接 `COM4`
2. 十六进制显示模式
3. 等待看到来自 `collector` 的请求：

```text
01 03 00 00 00 02 C4 0B
```

4. 收到后立即发送：

```text
01 03 04 02 92 FF 9B 5A 3D
```

注意：

- `collector` 串口读取超时是 `500ms`
- 最好在收到请求后尽快返回

### 8.2 自动应答

如果你的串口工具支持“收到指定报文后自动回复”，建议配置：

- 匹配请求：

```text
01 03 00 00 00 02 C4 0B
```

- 自动回复：

```text
01 03 04 02 92 FF 9B 5A 3D
```

这样 `collector` 每秒轮询一次时都会得到有效数据。

## 9. 预期现象

### 9.1 collector 侧

应看到类似日志：

```text
已发送认证请求
认证成功
采集成功: Device[0x01] Temp=-10.1℃, Humidity=65.8%RH
```

### 9.2 gateway 侧

应看到类似日志：

```text
收到认证请求: rtuId=ZM611116
RTU ZM611116 认证成功并已启用
RTU ZM611116 - 温度: -10.1℃, 湿度: 65.8%RH
```

### 9.3 PostgreSQL 侧

认证成功后可检查：

```sql
SELECT rtu_id, online, heartbeat_time
FROM rtu_gateway
WHERE rtu_id = 'ZM611116';
```

预期：

- `online = ONLINE`

### 9.4 MQTT 侧

可订阅以下主题验证：

```text
iot/rtu/ZM611116/data
iot/rtu/ZM611116/status
iot/system/online
iot/system/offline
```

如果你用 Mosquitto，可以这样看：

```powershell
mosquitto_sub -h localhost -t "iot/#" -v
```

## 10. 当前不建议测的内容

下面这些现在测了也不会是完整闭环：

1. `GET /api/data/realtime`
2. `GET /api/data/history`
3. `GET /api/data/statistics`
4. 从 `web-server` 发布配置，再让 `gateway` 订阅并下发到串口设备

原因：

- 前三者还是 mock
- 配置下发的 MQTT 订阅分发逻辑还没写完

## 11. 常见问题

### 11.1 认证失败

优先检查：

1. 数据库里 `rtu_id` 和 `secret` 是否与 `serial-collector` 配置完全一致
2. `web-server` 是否启动在 `8081`
3. `gateway` 配置里的 `web.server.api.url` 是否也是 `http://localhost:8081`

### 11.2 串口没数据

优先检查：

1. 虚拟串口是否成对创建成功
2. `collector` 打开的是不是你预期那一端
3. 串口模拟器是不是打开了配对的另一端
4. 波特率是否一致，当前默认 `4800`

### 11.3 手工发了响应也没被采到

优先检查：

1. 你是不是在 `collector` 发出请求之后 `500ms` 内回复
2. 回包 CRC 是否正确
3. 回包是否使用十六进制模式发送
4. 回包长度是否正好 `9` 字节

## 12. 建议的下一步

如果你下一步想继续把测试闭环补全，优先级建议是：

1. 给 `web-server` 增加 MQTT 订阅和数据落库
2. 实现 `realtime/history/statistics` 三个真实接口
3. 实现 `gateway` 的配置主题订阅和下发到串口设备
